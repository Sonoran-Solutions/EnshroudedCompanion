The strict selector resets `exact_build_match`, fingerprints the process image, loads candidates only if they contain `ecsLayout` and `hooks`, requires exactly one candidate matching target, timestamp, image size, SHA-256, and approved execution provenance, then calls `ReadGameProfile` (`modules/game-runtime/native/profiles/select_game_profile.cpp:13-16,47-64,92-134`). Missing/ambiguous exact profiles refuse at lines 124-128. Therefore the read-validated 26082781 profile does not authorize the scheduler hooks; the old 1076226 execution profile does not authorize this current image. The source path must remain a refusal until a matching execution profile is independently validated and approved. The owner's confirmation that the shared world is disposable/resettable is a useful session-safety prerequisite, but it does not substitute for this exact-image execution-profile gate.

If an approved profile is later selected, the read owner chain is:

1. `EngineContext::Configure` checks profile target and exact image SHA/timestamp/size, accepts `ownerLayout`, and only enables the ECS layout when `ecsReadLayout` has `ecsReadValidated` provenance (`modules/game-runtime/native/engine-context/configure_engine_layout.cpp:6-15,62-84`).

4. ## Hook callback contract and limits of static evidence

`EngineHooks::Install` installs a game-thread drain and entity-manager capture as mandatory hooks. It then tries prop-update, actor-placement, and building-dispatch hooks; `entity_context_hooks_ready` is true only if all three succeed. Cursor readiness is tracked separately. Initialization installs runtime patches after setting the dispatcher accepting (`engine-hooks/install_engine_hooks.cpp:175-227`).

The callback stubs are not one generic context contract:

- `callback_code` saves flags, RAX/RCX/RDX, R8-R11, and XMM0-XMM5, passes R15 as RCX and RBP as RDX, then restores those saved values (`install_engine_hooks.cpp:45-68`). That is an explicit call-site contract; the comment identifies it as the validated actor callback convention.
- `context_callback_code` reserves `0x88`, saves the same volatile state, reads the saved entry RCX into callback RCX, passes zero in RDX, restores state, then returns to replay (`install_engine_hooks.cpp:101-122`). This supports only its profile-specific building-dispatch entry contract. It does not prove that R15/RBP at the scheduler site represent valid arguments or that this stub can replace the generic dispatcher context.
- `cursor_callback_code` derives its arguments from R14, R13, and RBP for its own profile-verified cursor call site (`install_engine_hooks.cpp:70-99`). This also is not a transferable dispatcher contract.

The callbacks preserve flags and volatile registers explicitly; R15/RBP and other nonvolatile GPRs rely on the Windows x64 callee-save ABI. Statically, no generated stub registers dynamic unwind metadata. The hook installer copies the profile's `original_size` bytes verbatim into the trampoline and jumps back; there is no instruction decoder or relocation of copied relative branches/RIP-relative operands (`install_engine_hooks.cpp:125-171`). The profile byte/signature checks prove an expected byte sequence only; they do not prove the overwrite ends on instruction boundaries or that copied instructions are position-independent. Disassembly and instruction-boundary/relocation analysis for the exact current image are prerequisites.

Stack alignment also depends on the actual call-site entry RSP. With an ordinary Windows x64 function-entry alignment (`RSP % 16 == 8`) and the eight pushes in these stubs, `0x88` leaves the callback call-site aligned while `0x80` does not. The generic and cursor stubs reserve `0x80`; this is a concrete static question to resolve from the exact hooked instruction and its stack state, not a claim of a demonstrated runtime fault. A safe probe must validate alignment and the 32-byte shadow-space/stack-argument layout at its real site. Stub calls do `cld`, so restored flags must also be checked against the target’s continuation assumptions.

The patch writer prepares handles before suspending other process threads, suspends them, checks their RIP is outside the patch range, validates expected bytes, writes, flushes the instruction cache and resumes threads (`engine-hooks/write_executable_bytes.cpp:8-56`). Uninstall disables/reset state, restores hooks in reverse order, and intentionally retains trampolines so a returning thread does not jump into freed memory (`install_engine_hooks.cpp:230-248`). These are useful protections, but static review cannot prove scheduler quiescence during shutdown, prevent every race with a callback already inside the trampoline, establish safe unwinding from generated code, or verify engine threads do not hold locks that make suspension unsafe. Teardown and concurrent dispatch require explicit runtime evidence.

The dispatcher itself serializes drain callbacks with an atomic flag, bounds each drain to at most eight jobs or two milliseconds, bounds the queue to 128, rejects inline invocation outside active callback depth, and gives queued callers timeout/cancel behavior (`game-thread/run_game_thread_operations.cpp:14-78,120-176`). A timed-out job already executing can continue against its retained buffers (lines 144-155), so callers must not infer that timeout cancels a running operation. This is especially important for writes and cleanup.

## Minimum no-op scheduler probe acceptance constraints

This is a proposed acceptance contract, not authorization to execute it. A production hook continues to require the full exact approved execution profile described above. A deliberately separate typed diagnostic target could instead have its own exact-image diagnostic descriptor; it must not flow through production profile selection, claim production `runtimeLayoutValidated`, configure EngineContext/EcsRuntime, or enable any native action. Before installing such a diagnostic hook, require all of the following:

1. A post-update executable identity (path, timestamp, image size, SHA-256) and an explicitly diagnostic-only descriptor for that identity. The current read-only profile is insufficient for production execution hooks, and the older `1076226` layout must never be reused as a diagnostic descriptor for a different identity. No production approval flags are copied or inferred.
2. Exact-site evidence for the scheduler callback: unique executable signature, expected original bytes, decoded instruction boundaries covering the overwrite, disassembly showing no unrelocated relative/RIP-relative instructions, call-site RSP alignment/shadow-space, callback arguments and thread/phase semantics. Confirm the specific stub used; do not substitute the RCX-only `context_callback_code` for the R15/RBP generic convention. Sol's static chain review reports both worker and inline execution paths, so telemetry must support concurrent callers and cannot assume a sole game thread.
3. No-op semantics: callback performs no ECS queries, memory reads/writes, allocation, logging, UI, registration, synchronization that can block, or command dispatch. A fixture-level capture primitive now exists for a bounded, no-reuse tuple of raw iterator identity and caller-supplied thread ID; that does not establish which registers carry those fields or how a runtime hook would obtain a thread ID. Trampoline must replay the verified instructions exactly and restore flags/registers; callback exception/unwind behavior must be safe or proven impossible. Keep callback module and trampoline pinned until process exit unless a tested quiescence protocol is added.
4. Validate installation refusal on wrong hash, missing/ambiguous signature, byte mismatch, invalid overwrite, and failed write. Validate clean shutdown while idle and while a callback is pending/in progress, with no stale queue work or freed callback target. Runtime evidence must include exact identity, hook counters, dispatcher status, shutdown result, and relevant error logs, with no gameplay mutation.
5. Owner/session criteria are separate from scheduler-thread evidence. Observe stable owner/scene/UUID/manager/session through load, world transition and reconnect/reopen; prove stale or mismatched session work is rejected before any action. Only after the owner-authorized disposable session reset has been performed and observed should later P0 mutation cases proceed.

## Static findings versus required measurements

Static source establishes strict image/profile refusal, the intended owner/session checks, callback register/argument construction, bounded dispatcher behavior, and patch/unpatch safeguards. The host-only fixture under `probes/p0-scheduler-fixture/` passes ordinary, ASan/UBSan, and TSan tests for concurrent publication, saturation, and disabled capture; it is not wired into ShroudForge. This cannot establish current executable identity post-update, actual hook-site uniqueness/instruction semantics, register/stack state, scheduler frequency/phase, owner selection under real transitions, timing bounds under load, shutdown quiescence, or safety of later in-game writes. No runtime hook or live game test was run for this review. **All live P0 mutation cases remain `NOT_RUN` pending exact post-update execution-profile approval and the approved disposable-session reset. No live diagnostic hook has been installed; it could use a distinct exact-image diagnostic descriptor, but still requires the site/ABI/lifetime evidence above.**


## Synthetic entry adapter continuation

The new [entry fixture](../../probes/p0-entry-fixture/README.md) tests a separate generated adapter under isolated Proton Wine. It is not part of production profile selection and grants no runtime authority. The first passing fixture preserved volatile GPRs, XMM0–5, arithmetic/direction flags, raw RCX and call alignment/shadow space, with registered virtual-unwind checks at 12 boundaries. The `popfq` after stack restoration needs a separate unwind range. A subsequent continuation-transfer test exposed an epilogue-recognition hazard; the current fixture report records the corrected or blocked result. Do not generalize the earlier simpler fixture's pass to the continuation case.

The platform contract is grounded in Microsoft's [x64 exception handling](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64?view=msvc-170) and [prologue/epilogue rules](https://learn.microsoft.com/en-us/cpp/build/prolog-and-epilog?view=msvc-170), accessed 2026-10-22. Generated nonleaf code needs registered unwind data, and epilogue recognition constrains restoration and jump forms. Virtual-unwind fixtures exercise only the selected synthetic contexts; raised SEH, native Windows and live cleanup remain untested.

## Final diagnostic composition review

The separate [diagnostic build](../../probes/p0-shroudforge-diagnostic/README.md) now uses the strict bootstrap identity/startup gate, the shared ABI adapter and bounded telemetry, without enabling production runtime actions. The final adapter covers seven signed displacements including -200 and 301 virtual-unwind contexts. Publication checks 64 loaded bytes (entry plus continuation), expected metadata and a unique executable match, then rechecks bytes with peers suspended. Disabled callbacks return before thread-ID lookup; post-disable snapshots explicitly do not claim quiescence. Sol implemented the integration; parent reviewed ownership/cleanup and corrected continuation checks; Luna independently reviewed the final boundary.

There is no blocker to an owner-operated offline reset check with this DLL absent. That verifies only the operational prerequisite. Actual game admission/cadence, raised-exception behavior, exhaustive platform-failure injection and thread-creation races remain untested. A live diagnostic requires its own exact artifact/job/cleanup record; synthetic passes do not grant production execution approval. The private backup rehearsal verifies copies, not active-save restoration or game-level recovery.
