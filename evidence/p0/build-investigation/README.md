# Isolated native P0 build investigation

This reproduces the Windows x64 native provider and bootstrap cross-build for the pinned ShroudForge source at `3ed90de1df266c4f0c217523a02a71dfa67243de`, with the P0 guard changes already present in the source-review checkout. It is a source/build check. No real Enshrouded executable, installation directory, game prefix, or live process was opened or changed; synthetic hosts were used for refusal checks.

The cross toolchain is isolated under `/tmp/enshrouded-p0-toolchain`: Clang 21.1.8, MinGW-w64 GCC/C++ 13-posix and headers, CMake 4.2.3, Ninja 1.13.2, plus the pinned Zydis source and nlohmann JSON gitlink. Its packages were extracted locally; no system installation was used. The generated toolchain file is `/tmp/enshrouded-p0-toolchain/mingw-clang-toolchain.cmake`.

`patches/shroudforge/0002-p0-cross-build-portability.patch` contains only the portability changes needed here: the generated resource script no longer includes an unnecessary Windows header and uses numeric RCDATA IDs for bundled license files; the output DLL prefix is empty so the artifact name matches the bootstrap's `kfc-runtime.dll` lookup; server log opening explicitly uses `std::filesystem::path` for the wide path under Clang+libstdc++.

The CMake configure and provider build passed. Reproduction commands (paths are specific to this isolated toolchain):

```sh
ROOT=/tmp/enshrouded-p0-toolchain/root
export LD_LIBRARY_PATH="$ROOT/usr/lib/x86_64-linux-gnu:$ROOT/usr/lib/llvm-21/lib"
export PATH="$ROOT/usr/bin:$ROOT/usr/lib/llvm-21/bin:$PATH"
CXXFLAGS="--ld-path=$ROOT/usr/bin/x86_64-w64-mingw32-ld -L$ROOT/usr/lib/gcc/x86_64-w64-mingw32/13-posix -L$ROOT/usr/x86_64-w64-mingw32/lib -isystem $ROOT/usr/lib/gcc/x86_64-w64-mingw32/13-posix/include/c++ -isystem $ROOT/usr/lib/gcc/x86_64-w64-mingw32/13-posix/include/c++/x86_64-w64-mingw32 -isystem $ROOT/usr/lib/gcc/x86_64-w64-mingw32/13-posix/include/c++/backward -isystem $ROOT/usr/x86_64-w64-mingw32/include -isystem /tmp/enshrouded-p0-toolchain/json-src/single_include -fms-extensions"
cmake -S /tmp/enshrouded-p0-source-review/shroudforge -B /tmp/enshrouded-p0-toolchain/full-native-build -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/tmp/enshrouded-p0-toolchain/mingw-clang-toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_FLAGS="$CXXFLAGS" -DCMAKE_RC_FLAGS=
cmake --build /tmp/enshrouded-p0-toolchain/full-native-build --target kfc-runtime -- -j2
```

The bootstrap Visual Studio project was not rewritten. All six translation units listed in ShroudForge.Bootstrap.vcxproj compiled with Clang/MinGW. build-bootstrap.sh reproduces this compile and link. It translates the 180 source pragmas into a temporary DEF file while preserving the literal c:\windows\system32\winmm.Function forwarder path, alias, and ordinal. Quoting the target in the DEF is required: GNU ld rejects the unquoted drive-colon syntax. The linked PE imports only KERNEL32.dll, msvcrt.dll, and USER32.dll. Its absolute forwarders were inspected with objdump and exercised on Proton/Wine 11: a synthetic executable called timeGetTime through a local file named winmm.dll, and the loader resolved the target to c:\windows\system32\winmm.dll (Wine builtin); the test process exited 0. Do not use the earlier unquoted winmm.Function candidate, which recursively targeted the local proxy. The quoted-target candidate is at /tmp/enshrouded-p0-toolchain/bootstrap-objects/winmm-quoted.dll. The bootstrap guard test used this exact candidate: unrelated synthetic host exit 0; synthetic host named enshrouded.exe refused by strict identity at DllMain (Wine status c0000142, exit 66). Wine testing used WINEDLLOVERRIDES=winmm=n,b so the local proxy, not Wine's builtin winmm.dll, ran.

The provider PE is `/tmp/enshrouded-p0-toolchain/full-native-build/bin/kfc-runtime.dll`, ABI 12, with the expected `KfcRuntimeAbi`, `KfcRuntimeInitialize`, `KfcRuntimeTick`, `KfcRuntimeShutdown`, `KfcRuntimeStatus`, and `KfcRuntimeDiagnostics` exports. Its dynamic MinGW dependencies were staged alongside it under `/tmp/enshrouded-p0-toolchain/staged-bundle/shroudforge/`: `libgcc_s_seh-1.dll`, `libstdc++-6.dll`, and `libwinpthread-1.dll`. All three imports are present in each relevant dependency's import table and resolved from that staged directory during the provider test. `bcrypt.dll` and the remaining imports are Windows system libraries. SHA-256s are in `artifacts.sha256`.

Runtime refusal checks used Proton Experimental's Wine 11 in task-owned fresh prefixes under /tmp/enshrouded-p0-toolchain/, never the game prefix. The bootstrap forwarder call test and both DllMain checks passed with the quoted absolute system32 forwarders. The provider probe loaded ABI 12, called initialization from an unrelated synthetic process, and got profile=missing-exact-sha256-profile; hooks remained uninstalled. Captured output is in runtime-refusal-tests.txt.

These tests establish cross-build, loader entry, export availability, dependency resolution, and expected refusal on a synthetic image. They do not establish Windows-native runtime behavior or game compatibility. The current game profile remains unsuitable for execution: its validated profile has no `hooks`/`ecsLayout`, whereas the only execution profile targets an older executable identity. No game launch is warranted. The bootstrap static link emitted GNU linker duplicate-section warnings for C++ exception type metadata. Its exports/imports and absolute forwarders were checked, and forwarder invocation plus DllMain refusal passed isolated Wine tests; native Windows behavior remains unverified. The Rust runtime, launcher, updater and frontend have also built; see [Rust result](RUST_BUILD.md). The selected winmm-path binaries are staged locally, but no complete official release package, game deployment or successful native game initialization is claimed.
