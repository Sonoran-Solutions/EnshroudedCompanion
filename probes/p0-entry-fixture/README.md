# Synthetic Windows x64 entry adapter fixture

Run `timeout 120 probes/p0-entry-fixture/run.sh` from the repository root. It uses the existing isolated Clang/MinGW toolchain and Proton Experimental Wine, creates a fresh `/tmp/p0-entry-fixture.XXXXXX` prefix, runs only its synthetic host, kills that prefix's Wine server and removes its temporary directory. Compiler/linker/Wine versions and the synthetic EXE SHA256 are emitted before cleanup. No game prefix, executable, process, hook, profile or upstream source is opened or changed. No binaries are committed.

## Pure fixture builder and exact contract

`entry_adapter.h` provides `entry_adapter_build(EntryAdapter*, const EntryParameters*)`. Parameters explicitly contain callback address, continuation address and an exact overwrite byte span. Success returns a private byte image, three relative `RUNTIME_FUNCTION` records and instruction-boundary test points. It performs no allocation, protection change, registration or publication. Every refusal leaves the caller's output unchanged; the fixture tests 26 invalid inputs before its first executable allocation.

The only accepted overwrite is an 11-byte fixture shape: two-byte `REX push RBP`, one-byte `push RBX`, and eight-byte `lea RBP,[RSP+disp32]`. The signed displacement must lie in [-240,240] and be divisible by 8. The required -200 case is supported explicitly. LEA computes a pointer without allocating stack; its displacement is not a Windows unwind frame offset. The encoding is a strict shape match, not arbitrary instruction decoding or relocation. Unsupported opcodes, relative branch, RIP-relative LEA, truncated/oversized spans, null addresses and invalid displacements refuse. All input bytes/displacements in this fixture are fixture-owned; matching these lengths does not identify game semantics.

The adapter pushes flags, allocates 256 bytes, saves RAX/RCX/RDX/R8-R11 and XMM0-XMM5 outside the callback's 32-byte shadow area, clears DF and calls the callback with unmodified incoming RCX. The callback overwrites all four callback shadow words and deliberately destroys volatile registers/XMM values and arithmetic flags. Before restoring state, the adapter stores the continuation address in the original caller's first shadow word, exactly `[entry RSP+8]`. After state restoration and replaying the two pushes/LEA, `jmp [rsp+24]` reads that word without changing flags/registers or stack depth. The original synthetic remainder pops RBX/RBP and returns.

This transfer **requires the ordinary Windows x64 function-entry ABI and caller-allocated shadow space**, whose contents are callee scratch. It does not preserve that first original shadow word. The fixture checks the other three home words, return address and first stack-argument slot remain intact. A real candidate must independently establish that ABI and that no special contract requires preinitialized shadow contents. No live installability is inferred.

## Unwind boundaries and rejected transfer

Three generated ranges describe the main adapter, the one-byte `popfq` after stack deallocation, and the copied synthetic RBP/RBX/LEA prologue plus jump. A fourth fixture-owned range describes the original synthetic remainder. The separate `popfq` range is necessary because `add rsp; popfq` is not a recognized Windows epilogue. The copied range uses only PUSH_NONVOL entries for RBP and RBX, with frame_register=0. There is no SET_FPREG: LEA changes RBP while RSP remains fixed. Caller recovery uses RSP and the saved registers, including after the negative-displacement LEA and at continuation. The synthetic remainder likewise has no frame register. An earlier fixture version incorrectly limited the displacement to nonnegative frame offsets and used SET_FPREG; the current fixture corrects that model.

An attempted ordinary `jmp [rip+0]` failed its fixture: Wine's `RtlVirtualUnwind` recognized its ModRM mod00 encoding as a tail-jump epilogue, despite the copied pushes still being live. It returned saved RBX as RIP instead of the caller return address. That rejected transfer is retained as an independent **never-executed** negative unwind control in `fixture.c`; it reproduces the wrong saved-RBX result for each tested signed displacement. The corrected `jmp [rsp+24]` uses ModRM mod01, which avoids that epilogue interpretation. The negative control does not publish or execute a hook.

The test calls `RtlLookupFunctionEntry` and `RtlVirtualUnwind` at every emitted adapter instruction start, copied prologue/control-transfer boundary and synthetic remainder instruction start. Seven signed LEA displacements (-240,-200,-8,0,8,32,240) each pass 43 boundary checks, totaling 301. Six additional refusals cover displacement bounds, signed extremes and invalid alignment. Caller RIP/RSP and saved RBP/RBX recovery are checked wherever applicable. Volatile/flags preservation is checked by actual synthetic execution, independently of virtual unwinding. The table remains registered until all fixture invocations finish, is then unregistered, and the allocation is freed. This is single-thread fixture ownership, not production quiescence.

## Evidence and limits

`result.txt` records the final version/build hash and passing host output from 2026-10-22. `baseline-result.txt` retains the earlier 12-boundary nonreusable fixture result. Initial baseline fixture flags comparison failed because its synthetic sub/add body changed flags after adapter restoration; the corrected synthetic bodies use pushes/LEA/pops so the observation actually measures restoration. The transfer failure above was a separate material unwind issue and is now an explicit negative test.

Cross-build uses `-Wall -Wextra -Werror`. The final isolated Wine host exits 0. No native Windows run, raised exception/SEH dispatch, handler search, C++ exception, nested unwind, callback exception, arbitrary-PC fuzzing, concurrency, MXCSR/x87/extended-vector-state test, general relocator, actual game prologue, detour installation/removal, loader integration or game observation is claimed. Nonvolatile registers/XMM6-XMM15 rely on callback ABI compliance. A future callback needs an enforced no-throw contract or stronger exception evidence. Current execution remains HOLD; game runtime gates remain NOT_RUN.
